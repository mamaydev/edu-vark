Status: **backend SELESAI dan terverifikasi (23 berkas / 189 tes lulus). Android
SELESAI pada level kompilasi + unit test (24 berkas / 96 tes lulus, termasuk 27 tes

Tanggal: 2026-11 (baseline `b7b6cd6`). Pemilik: `p5-ui-validation` (paket 5).

## 1. Ringkasan

Lima celah fungsional ditutup tanpa menambah/mengubah endpoint backend:

1. **Edit topik (FR-009 / DEC-002):** layar dosen sekarang menyunting topik yang sudah
   ada lewat `PATCH /api/v1/lecturer/topics/{id}` pada **ID yang sama** (judul dan/atau
   deskripsi), bukan membuat topik baru. Status publikasi dipertahankan; perubahan
   diambil ulang dari server sehingga tetap terlihat setelah layar dibuka kembali.
2. **Paginasi & urutan (FR-017):** repository Android mengambil **seluruh halaman**
   (pageSize 100, batas aman 100 halaman) sebelum mengirim daftar lengkap ke endpoint
   reorder, sehingga urutan yang disimpan dosen tidak terpotong pada kelas dengan
   >50 topik. Mahasiswa membaca urutan tersimpan yang sama dari server.
3. **Empty state vs error (FR-016 / C1-03):** topik PUBLISHED tanpa materi aktif untuk
   kategori VARK mahasiswa menampilkan teks Indonesia **persis**
   `materi belum tersedia, harap hubungi dosen terlebih dahulu` (dan padanan Inggris).
   Pada jalur Kinesthetic pesan tampil **tanpa** menyembunyikan studi kasus. Kegagalan
   jaringan/server dirender sebagai kartu error terpisah + tombol coba lagi, bukan
   empty state.
4. **Validasi nilai manual (FR-043):** input nilai hanya menerima bilangan bulat 0–100
   dan komentar opsional ≤1.000 karakter. Input tidak valid **tidak** di-clamp,
   dipotong, atau difilter diam-diam — pengguna melihat pesan error dan nilai tidak
   berubah. Dialog konfirmasi dan sifat final penilaian dipertahankan.
5. **Panjang jawaban (FR-047 / C1-04):** batas 1–10.000 **Unicode code point** setelah
   trim, dengan satuan yang sama di penghitung Android, validasi ViewModel, dan API.
   Zod `submitCaseSchema` berhenti memaksakan `.max(10000)` berbasis UTF-16; otoritas
   panjang ada di service (`[...trimmed].length`) yang setara dengan
   `char_length()` PostgreSQL.

Regresi yang diverifikasi ulang: pengiriman final hanya sekali (sekuensial &
konkuren), status tanpa submission, kunci deadline setelah pengiriman pertama,
deadline inklusif berbasis waktu mulai transaksi DB, dan rollback penilaian yang
tidak mengubah teks jawaban maupun timestamp pengiriman.

## 6. Risiko dan batasan

1. **Unit test Android terbukti lulus; instrumentation belum dieksekusi.** Kompilasi
   main+unit test dan seluruh 96 unit test (24 berkas) lulus; `compileDebugAndroidTestKotlin`
   juga lulus. Namun `connectedDebugAndroidTest` tidak dijalankan P5, sehingga klaim
   tingkat UI/perangkat tetap NEEDS VERIFICATION.
2. **Build dir bersama sempat rusak** oleh Gradle paralel (error "error reading
   .../generated/ksp/...java" dari `compileDebugJavaWithJavac`); sempat juga muncul
   `NoSuchFileException ... test-results/.../results-generic.bin` saat beberapa run Gradle
   bertumpuk. Verifikasi akhir dilakukan serial dan lulus.
3. **Instrumentation test ringan** (bukan end-to-end penuh): memakai `createComposeRule`
   dan memverifikasi teks/aturan validasi, bukan alur Hilt + jaringan. Verifikasi UI
   perangkat (AT-04/11/15/23) tetap NEEDS VERIFICATION.
4. **Paginasi Android** memakai pageSize 100 dan guard 100 halaman; kelas dengan
   >10.000 topik akan terpotong. Backend membatasi `pageSize` maksimum 100, sehingga
   guard ini wajar; jika `meta.total` tidak tersedia, loop berhenti saat `data` kosong.
5. **Satuan trim:** Kotlin `trim()`, JS `trim()`, dan trim service backend sepakat untuk
   whitespace Unicode umum (termasuk NBSP); service men-trim sebelum menyimpan sehingga
   `char_length()` PostgreSQL mengukur teks yang sudah ter-trim. Perbedaan teoretis
   hanya pada karakter kontrol non-whitespace yang tidak mungkin dikirim sebagai
   whitespace oleh ketiga runtime.
6. **String lama** `lec_assess_error_score_range` sekarang tidak dipakai (pesan diganti
   `p5_assess_error_score_integer` untuk menegaskan integer 0–100). Tidak berbahaya,
   dapat dibersihkan belakangan.
7. Tidak ada perubahan pada endpoint backend, migrasi, `assessments.service.ts`,
   `topics.*` backend, `.github`, Dokumen-SRS, DECISIONS, maupun RTM.

## 9. Addendum remediasi cross-check P5 (24 Nov 2026)

Menindaklanjuti temuan cross-check Lead pada Paket 5. Riwayat §1–§8 dipertahankan;
bagian ini mencatat perubahan tambahan, perintah nyata, dan hasilnya.

### 9.1 Temuan dan perbaikan

1. **Pengosongan deskripsi topik (FR-009/DEC-002).**
   Aplikasi memakai `Json { explicitNulls = false }` (NetworkModule), sehingga
   `UpdateTopicRequest(description = null)` sebelumnya **menghilangkan** field dari body
   dan backend menganggapnya "tidak berubah" — dosen tidak bisa mengosongkan deskripsi.
   Perbaikan:
   - `data/remote/dto/TopicDtos.kt`: `UpdateTopicRequest.description` kini `JsonElement?`.
     Resource `JsonNull` adalah nilai non-null, jadi JSON tetap memuat
     `"description": null`; nilai teks dikirim sebagai `JsonPrimitive`.
   - `data/repository/TopicRepositoryImpl.kt`: `updateTopic` mengirim
     `description?.let { JsonPrimitive(it) } ?: JsonNull`. `LecturerTopicsViewModel`
     tidak diubah (`description.trim().ifBlank { null }` kini berarti "kosongkan"), dan
     `FakeTopicRepository.updateTopic` meniru backend baru (null = kosongkan) untuk tes.
   - Backend sudah benar (tidak diubah): `topics.repository.ts` memakai
     `CASE WHEN $3::boolean THEN $4 ELSE description END`, sehingga `null` eksplisit
     mengosongkan dan field yang dihilangkan mempertahankan nilai lama. Diverifikasi
     lewat request HTTP nyata pada tes baru `topic-edit-and-archive.test.ts`.
2. **Propagasi kegagalan `Response<Unit>` (reorder/hapus).** Retrofit tidak melempar
   `HttpException` untuk `Response<Unit>`, jadi `executor.execute { api.deleteTopic() }`
   dan `api.reorderTopics()` sebelumnya menelan non-2xx dan UI tampak sukses.
   `TopicRepositoryImpl` sekarang menyuntik `Json` dan memakai helper yang sudah ada
   `Response<Unit>.toAppFailureOrNull(json)`; non-2xx menjadi `AppFailure.Api`
   (kode/pesan dari envelope server). `LecturerTopicsViewModel.delete` sudah menampilkan
   `actionError`; `move` sudah menampilkan gagal lalu `load()` (urutan server dipulihkan)
   — keduanya kini benar-benar tereksekusi saat backend menolak. Publish/unpublish memang
   bertipe `TopicResponse` sehingga sudah melempar `HttpException` (tidak diubah).
3. **Paritas trim Android vs ECMAScript (FR-047/C1-04).** `String.trim()` Kotlin tidak
   sama dengan `String.prototype.trim` JS: Kotlin **tidak** membuang BOM (U+FEFF), NBSP
   (U+00A0), FIGURE SPACE (U+2007), NARROW NBSP (U+202F), OGHAM SPACE MARK (U+1680),
   MEDIUM MATHEMATICAL SPACE (U+205F), IDEOGRAPHIC SPACE (U+3000), tetapi **membuang**
   U+001C–U+001F yang justru dipertahankan JS. `P5TextRules` kini menyediakan:
   - `ecmaTrim(value)` — padanan ECMAScript `trim`;
   - `normalizeAnswerText(answer)` / `normalizeCommentText(comment)` — API normalisasi
     untuk dipakai lapisan submit (backend tetap penentu akhir);
   - `answerLength`/`commentLength`/`parseScore`/`is*Valid` memakai `ecmaTrim`, sehingga
     counter Android kini konsisten dengan backend `[...str.trim()].length`.
   `StudentCaseViewModel`/`StudentCaseScreen` **tidak disentuh** (milik P2). Lead perlu
   me-wire `P5TextRules.normalizeAnswerText(...)` pada jalur kirim jawaban bila ingin
   body terkirim dalam bentuk ter-trim; validasi/counter sudah konsisten tanpa perubahan
   P2 karena method lama tetap ada.

### 9.5 Risiko dan catatan

1. **Kontrak `updateTopic` Android kini selalu menyertakan `description`** (null = kosongkan).
   Jalur edit dosen memang selalu mengirim judul + deskripsi, jadi ini aman; backend tetap
   mendukung PATCH sebagian (field dihilangkan), tetapi repository Android tidak lagi
   memakainya. Bila kelak ada pemanggil yang ingin "hanya ubah judul", perlu overload baru.
2. **Verifikasi tampilan gagal reorder/hapus di perangkat** belum dijalankan (unit-level
   sudah membuktikan state `actionError` + urutan pulih). Perlu dicek Lead di emulator:
   aksi naik/turun saat backend menolak, dan hapus topik bersubmission.
3. **Wiring normalisasi jawaban** belum dipasang di `StudentCaseViewModel` (dilarang
   disentuh). Counter dan validasi sudah konsisten; yang belum: body request dikirim
   mentah (backend tetap men-trim dan memvalidasi). Lead dapat memanggil
   `P5TextRules.normalizeAnswerText(answer)` saat menyambungkan P2.
4. **DB uji baru `eduvark_test_p5r`** dipakai khusus tes topik remediasi; `eduvark`
   produksi tidak disentuh. `ALLOW_TEST_DB_RESET=1` hanya untuk DB uji.
